# 已完成档案软删除设计

## 目标

允许患者从侧栏删除不再需要展示的已完成档案。删除采用软删除：档案从正常列表隐藏，但原问诊、基础资料、开放描述、补充问答、检查建议和审计数据继续保留，为后续恢复功能预留条件。

## 范围

本次实现包括：

- 对当前患者的已完成档案执行软删除。
- 从正常档案列表过滤已删除档案。
- 阻止通过旧链接查看已删除档案。
- 在患者侧栏增加删除入口和二次确认。

本次不包括：

- 已删除档案列表。
- 恢复已删除档案。
- 永久删除档案或关联问诊。
- 批量删除。
- 多患者登录和权限系统改造。

## 方案选择

在 `intake_reports` 表增加 `deleted_at` 字段，实现档案级软删除。该字段只表达“已完成档案不再对患者显示”，不复用 `intake_sessions.archived_at`；后者继续专门表达患者放弃未完成问诊。

不建立独立删除记录表，避免为当前单患者演示系统引入不必要的复杂度。

## 数据模型

为 `intake_reports` 增加：

- `deleted_at: datetime | null`：为空表示正常档案；有值表示已软删除。

通过 Alembic 迁移增加字段及 `(patient_id, deleted_at, created_at)` 组合索引。已有档案默认 `deleted_at = null`，升级后继续正常显示。

软删除不会修改或删除：

- `intake_sessions` 会话。
- `baseline_measurements` 基础资料。
- `intake_field_states` 完整度字段状态。
- `follow_up_answers` 补充问答。
- `recommended_exams` 检查建议。
- `audit_events` 审计事件。

第一版不增加 `deleted_by`，因为当前系统尚无真实登录用户；删除操作仍必须按照当前患者 ID 做数据隔离。

## Repository 行为

### 正常档案列表

`list_patient_reports(patient_id)` 只返回：

- `patient_id` 与当前患者一致。
- `deleted_at is null`。

结果继续按照创建时间倒序排列。

### 档案详情

`get_patient_report(patient_id, record_id)` 需要区分：

- 档案不存在或不属于当前患者：返回不存在。
- 档案属于当前患者但已删除：抛出明确的 `DeletedReport` 领域异常。
- 正常档案：返回原有患者档案快照。

### 执行软删除

增加 `soft_delete_report(patient_id, record_id)`：

- 校验档案存在并属于当前患者。
- 首次调用时写入 UTC `deleted_at`。
- 重复调用返回相同删除时间，保持幂等。
- 不级联删除任何关联数据。

### 自动保存约束

`get_report_for_session` 和 `save_report` 必须识别已经存在的已删除档案。相同会话再次触发自动保存时，不创建第二份档案，也不清空 `deleted_at`，从而避免已删除档案自动重新出现在列表中。

## FastAPI 接口

新增：

`POST /api/patient/records/{record_id}/delete`

成功响应：

```json
{
  "record_id": "...",
  "deleted_at": "2026-09-17T10:00:00"
}
```

错误语义：

- 不存在或不属于当前患者：`404 Not Found`。
- 访问已删除档案详情：`410 Gone`，返回患者可理解的通用提示，不泄露内部信息。
- 重复删除：`200 OK`，返回第一次删除的时间。

现有 `GET /api/patient/records` 自动过滤已删除档案。现有 `GET /api/patient/records/{record_id}` 通过全局异常处理返回 `410`。

## 前端交互

“已完成档案”每一项改为两部分：

- 主区域：点击继续查看档案详情。
- 右侧“删除”按钮：低强调度文字操作，不使用醒目的图标。

点击“删除”后弹出二次确认：

> 该档案将从列表隐藏，已有问诊数据会保留。确定删除吗？

确认后：

- 请求软删除接口。
- 成功后重新加载已完成档案列表。
- 若当前正在查看该档案，关闭档案详情并返回当前问诊页面。
- 若删除的是列表中的其他档案，当前主页面保持不变。

取消确认时不发送请求。接口失败时保留档案列表和详情，仅显示错误信息。请求进行期间禁用对应删除按钮，防止重复提交。

若用户通过旧页面或旧链接访问已删除档案详情，前端展示“该档案已删除”的提示，并关闭失效详情；不自动恢复、不创建新问诊。

## 状态与并发

- 前端使用独立的 `deletingRecordId` 标记正在删除的档案。
- 后端以数据库中的 `deleted_at` 为最终事实来源。
- 两个页面同时删除同一档案时，两个请求均成功并返回同一删除时间。
- 列表请求和删除请求并发时，前端在删除完成后重新拉取列表，以服务端结果校正界面。

## 测试与验收

### Repository 测试

- 正常列表过滤已删除档案。
- 软删除保持患者隔离。
- 重复软删除幂等。
- 已删除档案详情触发 `DeletedReport`。
- 关联会话、基础资料和问答仍存在。
- 相同会话再次保存不会恢复或复制档案。

### API 测试

- 删除接口成功返回删除时间。
- 重复删除返回相同结果。
- 不属于当前患者的档案返回 `404`。
- 已删除详情返回 `410`。

### 前端测试

- 已完成档案具有独立删除按钮。
- 删除前出现规定的确认文案。
- 删除成功后刷新列表。
- 删除当前查看的档案后关闭详情。
- 请求失败时不提前移除档案。

### 浏览器与数据库验收

1. 打开一条已完成档案。
2. 点击该档案的删除按钮并确认。
3. 确认档案从侧栏消失且详情关闭。
4. 直接访问原档案接口，确认返回 `410`。
5. 查询 MySQL，确认 `deleted_at` 已设置。
6. 确认关联会话、基础资料和问答记录仍然存在。
