# 未完成问诊续接与软归档设计

## 目标

让患者能够在侧栏看到尚未完成的问诊，并在刷新页面、关闭浏览器或后端服务重启后继续填写。患者不再需要的问诊可执行软归档：从日常列表隐藏，但数据库中的会话、问答和审计数据继续保留。

## 范围

本次实现包括：

- 查询当前患者未完成且未归档的问诊。
- 从侧栏恢复任意一条未完成问诊。
- 对未完成问诊执行软归档。
- 将“继续问诊”与“已完成档案”分区展示。
- 阻止已归档会话被继续填写。

本次不包括：

- 已归档问诊列表。
- 恢复已归档问诊。
- 物理删除问诊数据。
- 多患者登录与身份认证改造。

## 方案选择

采用 MySQL 中现有的 `intake_sessions` 作为未完成问诊的唯一事实来源。未完成状态不转换为正式档案，也不依赖浏览器 `localStorage`。

该方案复用已经实现的完整会话持久化和单会话恢复接口，能够跨浏览器刷新和服务重启恢复，同时保持“草稿会话”和“正式档案”的业务边界。

## 数据模型

在 `intake_sessions` 增加：

- `archived_at: datetime | null`：为空表示正常会话；有值表示患者已放弃并归档。

通过 Alembic 迁移增加该字段及面向患者未完成会话查询的索引。现有数据默认 `archived_at = null`，不改变已有会话可见性。

软归档不删除下列关联数据：

- 基础测量资料。
- 字段完整度状态。
- 开放描述与补充问答。
- 推荐检查。
- 审计事件。
- 已存在的报告数据。

归档时向会话审计信息追加 `session_archived` 事件，并保存归档时间。重复归档同一会话保持幂等，不重复写入审计事件。

## 未完成会话定义

“继续问诊”列表只返回同时满足下列条件的会话：

- `patient_id` 属于当前患者。
- `archived_at is null`。
- 没有对应的 `intake_reports` 正式档案。
- `phase` 不是已经结束的阶段：`completed`、`incomplete`、`escalated`。
- 已产生有效填写行为：至少已确认基础资料、提交开放描述或产生一条补充回答。

结果按 `updated_at` 倒序排列，最近操作的会话位于最前。仅由“新建问诊”生成、尚未提交任何内容的空白会话不进入列表，避免长期使用后产生无意义的空记录。

## 后端接口

### 查询未完成问诊

`GET /api/patient/sessions/unfinished`

返回精简列表项，不传输完整状态 JSON：

```json
{
  "session_id": "...",
  "primary_concern": "最近三个月体重增加……",
  "phase": "follow_up_chat",
  "stage_label": "第 2 轮补充",
  "updated_at": "2026-09-16T20:30:00"
}
```

主诉摘要优先使用 `open_answer`，为空时返回固定占位文案。摘要在服务端截断，防止侧栏载入过长文本。

### 软归档问诊

`POST /api/intake/session/{session_id}/archive`

行为：

- 校验会话存在并属于当前患者。
- 设置 `archived_at`。
- 追加审计事件并递增会话版本。
- 已归档会话重复调用时返回成功，不重复修改。
- 不执行级联删除。

### 已归档会话保护

单会话读取和所有状态变更入口都需要识别归档状态。直接访问归档会话时返回 `410 Gone`，前端提示该问诊已被放弃并创建新的空白问诊，避免通过旧链接误恢复。

## 前端交互

患者侧栏中的记录区域拆分为：

1. `继续问诊`
2. `已完成档案`

未完成问诊条目显示：

- 主诉摘要；未填写时显示“尚未填写主要困扰”。
- 当前阶段标签，例如“基础资料”“开放描述”“第 2 轮补充”。
- 最后更新时间。

点击条目后：

- 将 URL 中的 `session` 参数切换为目标会话 ID。
- 清理历史档案详情和临时输入状态。
- 调用现有单会话接口加载完整状态。
- 根据恢复后的 `phase` 自动进入正确页面。

当前正在打开的会话由前端从“继续问诊”列表中隐藏，避免同一内容在主工作区和侧栏重复出现；切换到其他会话后，原会话会重新成为可继续项。

每条未完成问诊提供低强调度的“放弃”操作。点击后弹出二次确认，明确告知“该问诊将从列表隐藏，已有数据会保留”。

归档成功后：

- 从“继续问诊”列表移除该项。
- 若归档的不是当前会话，当前页面不改变。
- 若归档的是当前会话，立即生成新会话 ID 并进入空白基础资料页。

第一版不显示已归档列表，也不提供恢复入口，但数据结构保留未来恢复能力。

## 状态刷新与错误处理

- 页面初始化时并行加载当前会话、未完成会话列表和已完成档案列表。
- 每次成功提交基础资料、开放描述或补充回答后刷新未完成列表，使阶段和更新时间及时更新。
- 自动保存正式档案成功后刷新两个列表，该会话应从“继续问诊”消失并出现在“已完成档案”。
- 网络或接口失败时保留现有列表和当前页面，仅显示错误信息，不进行乐观删除。
- 归档确认期间禁用重复操作，避免重复请求。

## 并发与一致性

沿用现有会话 `version` 乐观锁。归档操作在同一个数据库事务中更新归档时间、状态快照和审计事件。若另一页面已更新会话，后端返回现有并发冲突响应，前端重新加载列表，不覆盖较新的内容。

正式档案保存成功后，即使会话阶段数据存在短暂差异，也以是否存在 `intake_reports` 记录作为列表排除条件，确保同一问诊不会同时显示在两个区域。

## 测试与验收

### 后端

- 仅返回当前患者的未完成、未归档、无正式档案会话。
- 不返回完全未填写的空白会话。
- 按最后更新时间倒序返回。
- 阶段标签和主诉摘要正确生成。
- 软归档保留全部关联数据。
- 归档接口幂等且仅记录一次审计事件。
- 已归档会话不能继续读取或写入。
- 不同患者无法查询或归档彼此会话。

### 前端

- 两类记录分区显示且空状态文案正确。
- 点击未完成记录可以切换并恢复问诊。
- 放弃操作有二次确认。
- 归档非当前会话不影响当前页面。
- 归档当前会话后自动进入新问诊。
- 正式档案保存后会话从未完成区移除。

### 浏览器验收流程

1. 新建问诊并填写基础资料和部分描述。
2. 刷新页面，确认当前进度恢复。
3. 新建第二条问诊，确认第一条出现在“继续问诊”。
4. 点击第一条，确认恢复到正确阶段。
5. 放弃第一条并确认其从列表隐藏。
6. 直接访问第一条旧链接，确认无法继续填写。
7. 检查数据库，确认其会话、问答及审计记录仍然存在且 `archived_at` 已设置。
