        ### **具体来说，你问它一个问题之后，它内部做了什么？**
        
        1. **判断问诊进度**
            - 它会检查这次对话已经采集了几个维度的信息。
            - 如果还没问完，它会选出下一个该问的维度（比如“饮食”问完了，该问“睡眠”了）。
        2. **检索中医古籍（RAG）**
            - 当你问理论性问题（如“不寐是怎么回事”）时，它会先去你上传的古籍库里找最相关的条文。
            - 把古籍原文和你的问题拼接在一起，再发给大模型，这样它就能引经据典地回答你。
        3. **引导对话**
            - 它不会一次把所有问题都抛出来，而是像真正的中医一样，一轮一轮地追问。
            - 语气专业又亲切，让患者愿意配合完成整个问诊流程。
        4. **生成总结与辨证**
            - 当五个维度全部采集完成，它会：
                - 用 Markdown 表格汇总所有信息。
                - 给出初步的中医证型推测。
                - （如果加了自动辨证指令）自动进行辨证分析，给出证型诊断和用药建议。

    !image.png
    
    !image.png
    
    - 项目说明
        
        ## **什么是 Function Calling？用餐厅比喻秒懂**
        
        **Function Calling 就是给 AI 装上一个“呼叫按钮”，让它能主动打电话给外部服务。**
        
        - **之前的 AI**：只能靠自己的大脑（模型参数）回答问题，知识有截止日期，无法获取实时信息。
        - **现在的 AI（有 Function Calling）**：当它发现需要查实时信息、调用某个特定功能时，会“暂停对话”，跑去执行你定义好的工具（比如查天气、搜论文、调你的辨证接口），拿到结果后，再继续回答你。
        
        你在 Dify 里配的“自定义工具”，就是在教 AI：“当你需要查某某东西时，就打这个电话。”
        
        ---
        
        ## **第二步：在 Dify 上实操 —— 给助手添加一个“查天气”工具**
        
        我们用最简单的免费天气 API 来演示，让你快速看到 Function Calling 的效果。
        
        ### **1. 找一个免费的天气 API**
        
        访问 **https://open-meteo.com/** （完全免费，不需要注册 API Key，直接调用）
        
        我们要用它的接口：`https://api.open-meteo.com/v1/forecast?latitude=39.9042&longitude=116.4074&current_weather=true`
        
        - `latitude` 和 `longitude` 是城市的纬度和经度（上面是北京）。
        - 这个接口返回当前天气，JSON 格式。
        
        ### **2. 在 Dify 中添加“自定义工具”**
        
        1. 进入你的“扁鹊预问诊”应用编辑页。
        2. 点击左侧 **“工具”** → **“自定义工具”** → **“添加工具”**。
        3. 填写工具信息：
            - **名称**：`查询当前天气`
            - **API URL**：`https://api.open-meteo.com/v1/forecast`
            - **请求方法**：`GET`
            - **请求参数**（在 `Query Parameters` 区域添加）：
                - `latitude`：类型 `number`，描述 `纬度，例如北京为 39.9042`
                - `longitude`：类型 `number`，描述 `经度，例如北京为 116.4074`
                - `current_weather`：类型 `boolean`，默认值 `true`
            - **响应格式**：Dify 会自动解析，不需要手动填 Schema。
        4. 点击“保存”。
        
        ### **3. 修改提示词，让 AI 学会“看天气”**
        
        在“扁鹊预问诊”的提示词**末尾**，加入以下规则：
        
        text
        
        ```
        【外部工具调用规则】
        当患者的问题涉及天气、气温、是否会下雨等内容时，你必须调用“查询当前天气”工具来获取实时天气数据。
        调用时，请使用北京的经纬度（latitude=39.9042，longitude=116.4074），如果患者提到了其他城市，请使用该城市的经纬度（如不清楚，可询问患者所在城市）。
        获取到天气数据后，用亲切的语气向患者说明当前天气情况，并结合中医养生原则给出建议（例如降温时注意避风寒，高温时注意防暑）。
        ```
        
        ### **4. 发布并测试**
        
        1. 点击“发布”。
        2. 在聊天界面问：“今天北京天气怎么样？适合出去运动吗？”
        3. 观察助手是否显示 **“正在调用工具：查询当前天气”**，然后返回天气信息和中医养生建议。
        
        **当你看到工具调用过程时，你就真正理解了 Function Calling 的全流程。**
        
        ## **第三步：这个机制在你的中医 Agent 里能干什么？**
        
        一旦你掌握了 Function Calling，你老师任务书里的很多功能都能实现：
        
        - **诊前预问诊 → 诊中辨证**：把 `/tcm_diagnosis` 接口配成工具，让助手自动调用。
        - **论文检索模块**：把 Semantic Scholar API 或 arXiv API 配成工具，让助手根据用户输入的关键词，实时检索最新论文，返回标题和摘要。
        - **检查报告解析**：配一个 OCR 接口，患者上传检查报告图片，助手调用接口读取文字，自动填入病历。
        - **药物不良反应查询**：配一个药物数据库 API，实时查询副作用。
        
        ## **第四步：那 MCP 又是什么？（通俗版）**
        
        **MCP（Model Context Protocol，模型上下文协议）** 可以理解为 **Function Calling 的“国际标准接口规范”**。
        
        - **现在的自定义工具**：每个 API 你都要手动填 URL、参数、描述。如果 API 有一万个，你就得配一万次。
        - **MCP 要解决的问题**：让 AI 能自动发现和调用任何符合 MCP 标准的工具，就像 USB 接口一样，插上就能用，不需要你挨个配置。
        
        在 Dify 里，你可以通过 **“MCP 插件”** 接入外部服务（比如搜索引擎、数据库）。你老师任务书里提到它，是希望你了解这种更高级的集成方式。**但初期你不需要自己开发 MCP 服务，只需要知道它是什么，并学会使用 Dify 中现成的 MCP 插件即可。**

### 2.2 LangChain/LangGraph/DeepAgents 框架深入

- ①.基于 **LangChain** 框架和 **阿里云通义千问 API** 的 RAG（检索增强生成）问答系统
    
    !5f2b8c65d630cfedccb6aea8cefa83d5.png
    
    !image.png
    
    - 项目介绍
        
        这段代码实现了一个基于 **LangChain** 框架和 **阿里云通义千问 API** 的 RAG（检索增强生成）问答系统。它的核心功能是读取本地的《黄帝内经》文本，将其向量化后存入本地数据库，然后允许用户通过自然语言提问，系统会从文本中检索相关片段并交由大模型生成精准回答。
        
        以下是代码的逐模块详细解析：
        
        ### **1. 环境变量与模型初始化**
        
        - **API Key 校验**：代码首先从系统环境变量中读取 `DASHSCOPE_API_KEY`，如果没有配置则抛出异常，确保后续调用阿里云 API 时不会因缺少凭证而报错。
        - **模型实例化**：
            - `DashScopeEmbeddings`：用于将文本转换为向量（Embedding），这是实现语义检索的基础。
            - `ChatTongyi`：通义千问的聊天模型（这里使用的是 `qwen-turbo`），负责在检索到上下文后，结合用户问题生成最终的自然语言回答。
        
        ### **2. 文档加载与文本分割 (Loading & Splitting)**
        
        - **读取文件**：使用 Python 原生方式读取本地的 `huangdi_neijing.txt` 文件。
        - **文本切分**：大模型有上下文长度限制，且长文本不利于精准检索。代码使用 `CharacterTextSplitter` 将长文本切分为多个小片段（Chunk）。
            - `chunk_size=300`：每个片段最多 300 个字符。
            - `chunk_overlap=50`：相邻片段之间有 50 个字符的重叠，这能有效避免在句子中间截断导致语义丢失。
            - `separator="\n"`：优先在换行符处进行切分，尽量保持段落语义的完整性。
        
        ### **3. 向量化与向量库存储 (Embedding & Storage)**
        
        - **构建向量库**：使用 `Chroma` 作为本地向量数据库。`Chroma.from_documents` 会调用前面初始化的千问 Embedding 模型，将所有切分好的文本片段转化为高维向量并持久化存储在 `./chroma_db` 目录下。下次运行时可以直接加载，无需重新向量化。
        
        ### **4. 构建检索器 (Retriever)**
        
        - 将向量库转换为检索器对象，并设置 `search_kwargs={"k": 3}`。这意味着当用户提问时，系统会在向量库中进行相似度计算，并返回与问题最相关的 3 个文本片段。
        
        ### **5. 构建 RAG Prompt 模板**
        
        - 定义了提示词模板，将大模型设定为“精通中医经典的专家”。
        - 模板中预留了 `{context}`（检索到的原文片段）和 `{question}`（用户问题）两个变量。
        - 加入了严格的约束指令：要求模型必须基于提供的片段回答，如果片段无关则如实告知，这能极大减少大模型的“幻觉”（即一本正经地胡说八道）。
        
        ### **6. 组装 RAG Chain (LCEL)**
        
        - 使用 LangChain 表达式语言（LCEL）以管道符 `|` 的形式串联了整个处理流：
            - `format_docs` 函数：将检索到的多个文档对象拼接成一段带有【片段 1】、【片段 2】标识的纯文本字符串，方便大模型阅读。
            - 数据流向：用户问题 -> 检索器获取文档 -> 格式化文档 -> 填入 Prompt 模板 -> 交给千问大模型 -> 解析输出纯文本。
        
        ### **7. 交互式问答循环**
        
        - 提供了一个 `while True` 的命令行交互界面。
        - **双重展示**：
            1. 先单独调用 `retriever.invoke` 打印出检索到的原文片段，让用户知道 AI 是基于什么资料回答的（增加了系统的透明度和可信度）。
            2. 再调用 `rag_chain.invoke` 获取并打印大模型生成的最终回答。
        - 支持输入 `quit`、`exit` 或 `q` 优雅退出程序。
        
        **总结**：这段代码结构非常清晰，是一个标准的“加载 -> 切分 -> 向量化 -> 检索 -> 生成”的 RAG 最小可运行示例，非常适合用来构建基于本地私有文档的专属知识库问答助手。

        ### **一、项目概述与配置**
        
        #### **1. 核心功能**
        
        - **历史记忆**：通过数据库（SQLite/PostgreSQL）持久化存储患者诊疗记录。
        - **辨证论治**：结合患者当前症状与舌象进行中医诊断。
        - **对比分析**：自动生成“初诊 vs 复诊”的对比报告，分析症状变化与处方调整。
        
        #### **2. 技术栈与环境**
        
        - **框架**：LangChain, LangGraph, DeepAgents, Pydantic。
        - **数据库**：支持 PostgreSQL（优先）和 SQLite（自动回退）双保险机制。
        - **LLM 模型**：优先使用千问云端 API (DashScope)，若无 API Key 则回退至本地 Ollama 模型（如 qwen3:8b）。
        
        ### **🛠️ 二、核心模块详解**
        
        #### **1. 数据库抽象层 (`Database` 类)**
        
        - **连接管理**：
            - 自动检测环境变量 `DATABASE_URL`，优先连接 PostgreSQL。
            - 若连接失败或未设置，则自动回退到本地 SQLite 文件 (`tcm_sessions.db`)，并开启 WAL 模式以支持并发读写。
        - **数据表结构**：包含患者姓名、就诊日期、症状、舌象、诊断、处方等字段。
        - **核心方法**：
            - `save_session`：保存新诊疗记录。
            - `get_last_session`：查询患者最近一次记录（用于判断复诊）。
            - `get_all_sessions`：查询患者全部历史记录。
        
        #### **2. 工具函数 (`@tool` 装饰器)**
        
        - **`get_patient_history`**：根据患者姓名查询历史记录，判断是“初诊”还是“复诊”，并返回上次的诊断与处方。
        - **`save_session_and_respond`**：
            - 保存当前诊疗数据。
            - 自动生成 Markdown 格式的诊疗报告。
            - **复诊逻辑**：若存在历史记录，生成包含“症状变化、辨证演变、处方调整”的对比表格。
        - **`retrieve_knowledge`**：基于预设字典的中医古籍检索（演示版），支持关键词匹配（如“恶寒发热”、“舌红苔黄”）。
        
        #### **3. Agent 构建与提示词**
        
        - **状态管理**：继承 `MessagesState`，扩展了 `patient_name`, `current_symptoms`, `diagnosis` 等中医特有字段。
        - **系统提示词 (`TCM_SYSTEM_PROMPT`)**：
            - **强制流程**：确认身份 -> 查询历史 -> 辨证论治 -> 保存报告。
            - **约束**：患者提供症状和舌象后必须直接辨证，禁止无意义追问；复诊必须对比历史变化。
        - **简化模式**：针对本地 8B 小模型提供了简化版提示词，以提升响应速度。
